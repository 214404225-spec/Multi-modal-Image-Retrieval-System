# 多模态图像检索系统

## 一、使用场景

**它解决什么问题？** 假设你有一个本地图像库，里面有几百上千张图片，你想用自然语言快速找到某张特定的图。比如你说"帮我找两张三只棕色站立狗的照片"，系统就能理解你的意图，从图库中精准定位到符合条件的图片。

传统的图像检索只能按文件名或标签搜索，但我的系统可以直接理解中文自然语言中的复杂条件——不仅仅是"狗"这个类别，还包括数量条件（"三只"）、颜色属性（"棕色"）、姿态属性（"站立"），以及返回多少张（"两张"）。

以下是一些典型的使用示例：
- "帮我找白色的狗" → 走常规检索路径，直接返回白色狗的图片
- "找站立的熊的照片" → 走细粒度检索路径，用视觉模型逐一验证候选图片中熊是否站立
- "帮我找 2 张 3 只猫的图片" → 走细粒度检索路径，确保每张图里恰好有 3 只猫
- "搜索狗的图片" → 走常规检索路径，直接返回狗的图片

系统提供两个入口：
1. **Web 前端**：浏览器打开即用，输入查询后实时看到检索进度和缩略图结果
2. **命令行交互**：适合开发调试

下面我按照用户输入到输出检索结果的顺序，逐个介绍系统的核心模块。

---

## 二、意图识别模块

**数据流的第一步**：用户输入自然语言查询后，首先进入**意图识别模块**。

这个模块的核心是用一个大语言模型——Qwen3-8B，通过 Ollama 本地部署——来解析用户查询中的结构化信息。我设计了一套 Prompt Template，要求模型输出以下字段：

- **是否需要检索**："帮我写首诗"这种查询就不需要检索，直接回复
- **检索类别**：比如"狗"、"熊"、"猫"
- **检索数量**：返回几张图片（比如"2张"→2）
- **物体数量**：图片里应该有几个物体（比如"3只猫"→3）。注意区分"张/幅"是图片量词，"只/个/条"是物体量词
- **属性条件**：颜色、姿态、场景、视角等

这个模块最大的工程挑战是**小模型的输出不稳定**。8B 参数的模型有时候会漏掉属性、误判数量、或者输出格式不规整。所以我写了一个多层的回退 parser：

- **第一层**：从 LLM 的结构化输出中直接解析
- **第二层**：LLM 漏掉类别时，从常见物体列表中回溯匹配
- **第三层**：LLM 误判数量时，用正则从原始 query 中提取数字覆盖 LLM 的输出

这种"LLM + 规则兜底"的设计，让意图识别的准确率从纯 LLM 的约 86% 提升到了 90.9%。

---

## 三、程序化路由决策

**数据流的第二步**：拿到意图后，系统需要决定走哪条检索路径。

这是一个关键的架构决策——**路由不由 LLM 决定，而是由代码确定性执行**。为什么？因为初版中我们让 LLM 自己选路径，结果小模型约有 5% 的概率选错。路由一旦错了，后面的检索全错。

我的路由逻辑非常简单，就是一个判断：

```
needs_vl = (有物体数量) 或 (有复杂属性)
```

- **复杂属性**指姿态（站立/坐着）、场景（室内/室外）、视角（正面/侧面）等 CLIP 无法可靠编码的属性
- **简单属性**指颜色、大小、明暗——这些 CLIP 可以直接处理，不需要 VL

这个设计把 LLM 的职责限制在它擅长的语义理解上，路径选择完全交给确定性代码，错误率为零。

---

## 四、常规检索路径 — CLIP-only

**数据流的第三条分支**：如果路由判断不需要 VL，就走常规检索路径。

这里我使用了 **Taiyi-CLIP** 模型，它是中文原生的双塔架构：

- **文本塔**：Chinese RoBERTa，原生支持中文编码，不需要翻译成英文
- **图像塔**：CLIP ViT-L/14，标准的视觉编码器
- 两个塔的输出通过投影层对齐到同一个 768 维 embedding 空间

**离线阶段**：系统启动时，先把图像库中所有图片用 ViT 图像编码器跑一遍，生成特征向量存入内存向量库。编码结果会缓存到磁盘（`cache/image_features.pt`），下次启动如果图像没变就直接加载，跳过重复编码。

**在线检索**：用户查询经 Chinese RoBERTa 编码为文本向量，与向量库中所有图像特征做点积相似度计算，取 Top-K 返回。

这里有一个重要设计——当用户输入"白色的狗"时，编码的不是裸"狗"，而是完整短语"白色的狗"。因为颜色是 CLIP 学得最好的属性之一，直接编码完整短语比先搜狗再过滤颜色更高效，也避免了后处理的信息损失。

这条路径耗时通常不到 1 秒，非常快。

---

## 五、细粒度检索路径 — VL 精排

**数据流的第四条分支**：如果路由判断需要 VL 精排（有物体数量或复杂属性），就走两阶段检索。

### 第一阶段：CLIP 粗排

跟常规检索不同，粗排阶段只用**裸类别**构建查询（比如只用"狗"不用"3只棕色站立的狗"）。为什么？因为 CLIP 对复杂属性的理解很粗糙，提前引入属性可能反而误杀 VL 模型能正确判断的候选。

粗排的候选池大小不是固定值，而是根据查询动态计算：
- 有物体数量时：`count × object_count × 2`，保底 30 张
- 无物体数量时：`count × 3`，保底 15 张

### 第二阶段：VL 精排

粗排返回的候选图片，逐一送入 **Qwen3-VL-8B** 视觉语言模型做二分类验证。

VL 的验证逻辑是把物体计数和属性条件**合并成一次调用**。比如用户查询"3只棕色站立的狗"，VL 的 prompt 就是：

> "请判断这张图片中是否恰好有 3 只棕色站立的狗。只回复「是」或「否」。"

这里有一个重要的设计演进值得讲一下。最初我设计的是一个分级评分方案——VL 输出 0.2~1.0 的连续分数，然后与 CLIP 分数加权融合。但实际落地时发现，8B 的小模型根本做不了可靠的分级评分，输出几乎全是 1.0 或 0.0。

所以我把策略简化为：**VL 只做二分类，通过则保留 CLIP 粗排分，不通过则直接剔除**。这不是理想方案，但这是把任务匹配到模型真实能力水平的务实选择。

VL 精排后的结果按 CLIP 粗排分排序，裁剪到用户请求的数量。

### 耗时和瓶颈

这条路径的主要开销在 VL 验证——每张图约 10-20 秒（本地 8B 模型推理）。30 个候选在最坏情况下需要约 7-10 分钟。我做了几个优化：
- 用 ThreadPoolExecutor 做单线程超时控制，60 秒超时自动放弃
- 超时后重置模型实例，避免 Ollama 排队卡死后续请求
- Web 前端通过 SSE 实时推送每张候选的验证进度

坦白说，VL 精排是目前整个系统最大的瓶颈——8B 参数的小模型在复杂属性组合下的判断能力确实有限。理想方案是用 GPT-4o 或 Claude 等 SOTA 多模态 API 替代本地小模型做精排，这也是我设计的混合架构演进方向。
